System design · India-wide ambition

One evidence system for every election.

Many government sources, one consistent model. Every public fact should have a traceable origin, a time context, and a clear path to correction.

Design boundary

This describes the target architecture. The current website holds manually curated records for two Lok Sabha areas. Connectors, a database, review tooling, and location matching are proposed, not yet implemented.

01 / Collect

Source adapter

Knows how to check one source, save its response and metadata, and detect a changed document. It cannot publish facts. A PDF page, HTML portal, downloadable file, and API each get an adapter suited to that source.

Publication rule

Conflicts stay visible to reviewers

Two source observations may disagree. Preserve both, flag the conflict, and keep the last approved public value until a reviewer resolves it. A later fetch does not silently overwrite a profile.

Unknown is a valid state. No source, failed extraction, or unresolved identity means the fact stays unpublished. Missing data is never filled from a name match or a model guess.

Relationship logic

Links have dates and evidence

Person → candidacy → contest

“Candidate” is a role in one specific contest, not a permanent type of person.

Contest → election → area

An election can include many contests, and boundaries may change between elections.

Person → term → office

Winning an election and currently holding office are separate claims.

Area ↔ area

Geography may have containment and overlap. Do not force every relationship into one hierarchy.

Where data lives

Begin with one backend and clear modules. Add infrastructure when volume or freshness measurements justify it.

Relational database

Entities, observations, approved facts, review decisions, versions and audit history.

Place matching

Spatial extension

Public delivery

Cached read views

Prebuilt profiles, area pages, comparisons, search and graph edges from approved records.

Location without a fragile PIN rule

With permission, use the browser position for a boundary lookup and return all relevant offices. Do not store precise coordinates by default. If a boundary is missing or a point is ambiguous, ask the citizen to choose an area. A PIN code can help search, but it is not proof of constituency membership.

Spatial point-to-polygon queries are a standard capability of PostGIS. We still need authoritative boundary data and a review process for each boundary version.

Different clocks for different facts

Keep effective time (when a fact applied), source time (when an authority published it), observed time (when we fetched it), and review time (when we approved it). Public pages should show the relevant review date and avoid saying “live” unless the source supports that claim.

Election-night trends, final results, nominations, office holders, parliamentary activity and citizen issues have different update speeds and certainty levels.
Freshness policy

Update by source and fact type.

These are proposed behaviors, not claims that every government source offers an API or a reliable update signal.

Scale path

Grow capacity without changing truth rules.

One source family

Build the contract, review screen and repeatable import for a small set of constituencies. Measure extraction and matching errors.

More adapters

Cache approved profiles and area views at the edge. Rebuild only affected pages or projections when facts change. Measure cost and latency.

For each fact

Evidence trail

Expose a stable fact ID, source and exact locator, captured and reviewed dates, transformation version, identity decision, publication revision and correction history.

For each area

Coverage and freshness

Publish which elections, offices and activity sources are covered, when they were last checked, and which records are missing or disputed.

For the platform

Open operations

Publish source catalog, schema, normalizer code, data releases, change log, review policy, corrections and source failures where safe to disclose.

Privacy boundary: public evidence and decisions can be inspectable without exposing private complaint details, precise citizen locations, protected personal data, credentials or abuse controls. When information is withheld, explain the category and reason.
Decide before implementation

The questions that shape the system.

Recommended defaults are design proposals. Research and source audits should settle them before we build the national pipeline.

Scope

What is an “election”?

Model election event and contest separately so Lok Sabha, assembly, local, by-election and indirect elections can fit without pretending their rules are identical.

Coverage

How do we say what is missing?

Keep explicit coverage by area, election, source and fact type. A missing candidate or activity record must not look like zero activity.

Authority

Which source settles a conflict?

Define precedence per fact type, plus human adjudication and correction history. Avoid one global “most trusted website” rule.

Identity

When can records be merged?

Require strong identifiers or corroborated context. Preserve aliases and reversible merge decisions; never merge solely on a matching name.

Geography

Which boundaries are authoritative?

Audit availability, licensing and version dates for constituency and ward maps. Until checked, provide manual area selection.

Governance

Who may approve a fact?

Set reviewer roles, double review for sensitive changes, dispute handling, and an audit trail before accepting broad community contributions.

Reuse

Can we keep and republish source files?

Check each source's terms and reuse rules. Always preserve metadata and a link; retain file copies only where allowed.

Ranking

How should comparisons work?

Keep scores as later, transparent derived views. Define meaning, coverage and bias tests before assigning any “good candidate” number.

Transparency

How far should public audit access go?

Define public claim traces, review decision fields, source copies, open exports and justified redactions before building review tools.

Recommended first build: one official candidate/result source adapter → immutable snapshot → normalizer → observation review → approved candidacy and result records → existing profile and area pages. This tests the whole architecture without claiming national coverage.
